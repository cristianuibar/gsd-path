# Multi-repo milestones — work plan

Design: [ADR 0002](adr/0002-multi-repo-coordinator.md).

## Contract

One milestone can define, plan, build, and ship work across several Git repos,
both new (greenfield) and existing (brownfield). One task changes one repo.
Every CLI takes one `--repo`, the coordinator. Joining a member adds no new
tracked Path files there and leaves an existing member `.project/` untouched.
Without `.project/MEMBERS.md`, behavior and output stay single-repo. Member task
execution stays disabled for users through S3c3b1; that slice proves gated
dispatch in a two-repo build. S5 removes the gate and activates the full
multi-repo workflow.

## Where Path assumes one repo

Function names, not line numbers, because main moves.

| Area | Current contract to change |

| Root and binding | `pipeline_state._repo_root`, `build_state._repo_root`, `pipeline_git._require_worktree_root`, and `isolation.worktree_root` use one Git root. `REPOSITORY.md` has a fixed single-repo format. |
| Strict STATE parsers | `pipeline_state._state_from_text`, `git_guard.strict_ship_state`, `guard_hook.valid_status_state`, and `install._valid_status_state` reject unknown fields. Do not add STATE `repos:`. |
| Branch pattern | `_common.BOUND_BRANCH_RE` accepts only `gsd-path/M00N`. Member `git_guard` dispatch handles coordinator-named refs separately. |
| Tasks and dispatch | `build_state._validate_ready_metadata` checks a base in the coordinator; `dispatch_driver.finish_task` reads the task file in the product worktree. See S3c3b1 for member dispatch. |
| Landing proof | `git_guard.product_commit_violations` enforces the single-repo landing shape; see S3c2a–S3c2b for member landing proof. |
| Verify ledger | See S3d for member and coordinator keys. |
| Sidecar placement | `worktree_paths._workspace` gives each repo a separate hashed root; `../<member>` does not resolve across them. |
| Guards | `guard_hook` applies the S2d member-write rules below. Member `git_guard` skips the member's own STATE as a commit gate; archive checks still apply. |
| Ship body | `git_guard.ship_contract_violations`, `archive_milestone.require_canonical_commit_body`, and `pipeline_undo._archive_metadata_error` require the current exact ship body. |
| Lookahead drift | See S3d for member plan handling. |
| Close and retirement | `integration.integrate`, `integrate_pull_request`, and `validate_integrated` close one repo. They need a STATE, archive, and ship commit in that repo, require the ship commit as the merge's second parent, and name the tag `milestone/<archive-name>`. `pipeline_git.bind_next_milestone_branch` and `retire_previous_branch` retire one branch. |

## Slices

Each slice ships in its own PR. Every slice changes all readers of any contract
it changes. A script that checks branch names accepts member names in the slice
that first runs it in a member: `git_guard` in S2b; `isolation`, `dispatch_driver`,
and `build_state` in S3c1-S3c3; `integration`, `archive_milestone`, `pipeline_undo`,
`pipeline_diagnose`, and `pipeline_git` retirement in S4. `STATE.branch` stays the
coordinator's `gsd-path/M00N`, so `pipeline_state` keeps its branch parser;
its build-entry transition locks member branches in S3b. Until then those
scripts refuse member names, which fails safe. S1–S4 leave the no-`MEMBERS.md`
path and output unchanged.

| S0 | This ADR and plan. |
| S1 Member contract | Add `scripts/members.py` with `add` and `validate`. `add` creates `.project/MEMBERS.md` if absent, including for a brownfield coordinator, without changing `REPOSITORY.md`. Validate clean worktree, GitHub `origin`, remote default `main`, no nested repo or submodule, no active member milestone, no unreadable member STATE, and no branch or tag collision. Reject a duplicate origin or Git common dir. Allow `MEMBERS.md` in `isolation.PROJECT_ENTRIES`, `lean_verification._require_ship_inputs`, and `archive_milestone.require_clean_active_root`. Define member identity and Coordinator/Member terms in `CONTEXT.md`. In S1, `add` only writes `MEMBERS.md`; the next approval checkpoint commits it. It refuses membership changes during build and ship. |
| S2a Member role | `members add` writes an untracked marker in the member's shared Git directory (`$(git rev-parse --git-common-dir)/gsd-path/member.json`) naming the absolute coordinator path, project, and member name. `members.member_role` verifies it from any worktree of the member: the coordinator exists, its project matches, and its `MEMBERS.md` lists this name at this Git common dir. No marker returns `None`, so single-repo behavior is unchanged; an unreadable or stale marker fails closed and names `members.py repair --repo <coordinator>`. `validate` checks every listed member's marker. `repair` rewrites missing, malformed, or stale markers (for example after the coordinator moves) and skips valid ones. `add` and `repair` refuse a marker from another project or one owned by a different coordinator that still verifies the member. The marker directory must be real; a non-regular marker path must be removed by hand before repair. |
| S2b Member guard and push | In member mode (a verified `members.member_role`), `git_guard` skips the member's own STATE as a commit gate, so its own unverified or closed milestones do not gate commits; archive immutability still applies and member commits get landing proof in S3c2. `members.member_ref_prefixes` names the refs a member reserves for its coordinator: `gsd-path/<coord>-`, `gsd-path-task/<coord>-`, `gsd-path-verify/<coord>-`, `gsd-path-integrate/<coord>-` branches and `milestone/<coord>-` tags. The coordinator records authorization for a ref and exact commit or annotated tag object under `refs/gsd-path/authorizations/<coord>/push/` in the member (`members.authorize_push`); member pre-push accepts a reserved ref only at its authorized object. Authorization remains until S4 clears it, since the hook cannot know whether a push succeeded. Any other ref (for example the member team's own `main` push) publishes unless it carries commits from a member bound branch that are not on `refs/remotes/origin/main`, which needs the same authorization. Joining and pre-push require that resolvable baseline; a missing ref fails closed with a `git fetch origin` hint. Deleting a reserved ref needs `members.authorize_delete` for that ref at its expected remote SHA. A stale marker blocks commit and push with the repair hint. |
| S2c Member install | `install.py --member-of <coordinator> --project <member>` (also through `install.mjs`) writes only Git hooks into the member's effective Git hooks directory, after `members.member_role` verifies that coordinator and its guard is installed. Each hook finds the coordinator through the member marker, so a moved coordinator needs only `members.py repair`, and runs the coordinator's `.gsd-path/git_guard.py`. An existing unmanaged hook is kept as `<hook>.gsd-path-chained` and runs after the guard passes (pre-push gets the same stdin); the member's own single-repo Path hooks are replaced, not chained. Install refuses a hooks path inside any member worktree, a symlinked or non-regular hook, and an existing chained hook it would overwrite. Rerunning is idempotent; `--dry-run` writes nothing. |
| S2d Member writes | `guard_hook` classifies a write into a verified member of this coordinator (any worktree of it, found through the member marker in its Git common dir) as product, so the coordinator's phase rules apply; a stale member of this coordinator is denied with the repair hint; repos without a marker, or members of another coordinator, stay external. Shell writes to product files are not phase-gated for either the coordinator or members; close this shared gap in a separate issue. |
| S3a Member task planning | Task `repo:` names a member from `MEMBERS.md` (absent means the coordinator). `check_task_briefs` checks a member task's `files`, prose, and Verify paths in the member (see S3c3b1 for revision selection); supplied `.project/` contracts still resolve in the coordinator. An unknown member is refused. `check_handoffs` compares same-wave overlap as `(repo, path)` and supplies dependency files only within the same repo. `members.py` ships in every skill that bundles `check_task_briefs`. |
| S3b Build start | On the active track's `plan/done` to `build/active` transition, read task `repo:` names and write `.project/build/members.json` with schema `gsd-path/member-lock/v1`, recording each named member's name, bound branch, and base in `MEMBERS.md` order. The build checkpoint commits the lock with STATE. Before creating refs, require a valid member marker, the recorded origin URL, `origin/main`, a safe lock path, and a lock file Git will track. Create each missing `gsd-path/<coord>-M00N` branch at `origin/main`; reuse an unused branch at its tip or a locked branch that descends from its recorded base, and refuse other existing branch work. If no task names a member, write no lock; on recovery re-entry, remove a prior lock but leave member branches for S4 retirement. A refusal leaves STATE unchanged. |
| S3c1 Member isolation | `isolation.member_bound_checkout` keeps Path's own checkout of a locked member's bound branch in the member's Path workspace (never the member team's checkout; refused when the team holds that branch). Member tasks always isolate in a `gsd-path-task/<coord>-<id>` sidecar at the bound checkout's tip (`member_base`) through `isolation.isolate_member_task`; `create_named_worktree` takes the member bound branch. `isolation.retire_member_task` removes an unused member sidecar. |
| S3c2a Member landing write path | `isolation.land_member` commits and proves the member source commit in the member sidecar (parent `member_base`, only the contract's `files`, subject from the contract, body `Task`/`Base: member_base`/`Contract: base`/`Files`), writes a journal in the coordinator Git directory, cherry-picks into the member bound checkout only while its tip equals the journaled parent, proves the landing against that parent, then makes a `.project`-only coordinator record commit (`Task`, `Base`, `Member: <name> <landing> <member_base>`) that stamps the task `done` with `base` and `member_base`. A coordinator-wide lock serializes member landings and record commits; another task for the same member is refused while a journal is pending. `isolation.recover_member_landing` finishes an interrupted landing from the journal: it picks only when the member branch still sits at the journaled parent, adopts an already-picked landing, writes the record only, and blocks when someone else moved the branch. A cherry-pick conflict leaves the member bound branch and coordinator unchanged; the task's source commit stays on its sidecar for retry. In member mode, `git_guard` refuses direct commits on the member bound branch; cherry-pick landings run `prepare-commit-msg` and `post-commit` hooks but skip the direct-commit guard. |
| S3c2b Member landing readers | `_recover_task` proves a done member task from exactly one coordinator record on the first-parent history. The record touches only the task file and stores it as `done`, with `base` and `member_base` matching the record body. Proof reads the member lock from the record commit and the task contract from the record Base; the current or archived task must retain that contract's `id`, `title`, `repo`, `files`, `deps`, and `wave`. It verifies the member marker and checkout, then proves the named landing on the member bound branch's first-parent history (building on `member_base`, changing only declared files, with the exact member landing subject and body). `verify_landed_task_files` and its callers accept proven member tasks even after the active task and lock move to the archive. See S3c3b1 for unfinished task recovery. `retire_member_task` also retires a task branch whose commits all landed by cherry-pick (`git cherry`). |
| S3c3a Member activation | `isolation.activate_member_task` requires a clean member sidecar at its task branch tip, with that tip contained in the member bound branch, and a pending coordinator task contract for the member at `base`. It writes the running task's live copy, stamped `in-progress` with a valid agent, `base`, `member_base`, worktree, and task branch, to `.gsd-path-coordinator/<task file>` in the member sidecar (untracked, excluded through the member Git directory's `info/exclude`), so the coordinator stays clean while member work runs. The copy path must be untracked, with real directories and a regular non-symlink file inside the sidecar. Activation records `refs/gsd-path/task-authorizations/<coord>-<id>` at `member_base`; retry reuses a copy only with the same agent, `base`, and `member_base`. `land_member` requires that authorization and copy (same contract fields, append-only body) and writes the record from it, so the coder's Log lands in the coordinator. The coordinator may keep unstaged bookkeeping changes, but no other dirt or staged files. Recovery also accepts its own task file if a partial record write left the exact stamped text unstaged or staged; other dirt still blocks. `retire_member_task` clears the authorization or reports deletion failure. |
| S3c3b1 Member dispatch | Member execution stays off until S5 through a temporary gate: `build_state` refuses member tasks unless `GSD_PATH_MEMBER_EXECUTION=1` (tests set it; S5 removes it). `build_state` tasks carry `repo`, compare overlap as `(repo, path)`, and `ready` names a member task's `repo`. Brief lint uses the locked bound branch tip whenever `.project/build/members.json` exists, including Plan recovery after build began; without the lock, it uses `origin/main` before the first build start. The lock is archived at ship, so a new milestone starts without it. The bound tip contains earlier member landings, like the coordinator head used to lint coordinator tasks. `dispatch_driver` isolates and activates member tasks through `isolate_member_task` and `activate_member_task`, briefs the coder with the live copy and the coordinator's INTENT, measures the Log against the contract, runs Verify in the member sidecar, lands with `land_member`, clears the authorization when Verify fails, retires the member sidecar, and finishes pending landing journals before recovery. See S3d for member Verify ledger records. `_recover_task` recovers unfinished member tasks: none without isolation, resume with a retained member task branch, landing retry for a pending journal, and block when a record exists for a task that is not done. An end-to-end round lands a coordinator task and a member task. |
| S3c3b2 Member sidecar hooks | `activate_member_task` writes, for each host whose managed hook config is installed in the coordinator (Claude, Codex, Cursor), an untracked config in the member sidecar, excluded through the member Git directory, that calls the coordinator's `.gsd-path/guard_hook.py` by absolute path, because inside a member sidecar the Git top level and project dir name the member. Before writing, activation refuses a symlinked config path or a config with different content (tracked or local), naming that path; identical configs can be reused. The driver cannot tell which host runs a coder, so every installed host counts. It checks these configs before every member coder launch, restoring missing ones and refusing changed ones, including on resume. |
| S3d Proof records | Verify ledger rows are keyed (command, repo, commit): a member row carries `"repo": "<member>"` and names a commit in that member; rows without `repo` are coordinator rows, so existing ledgers and single-repo output are unchanged. `_common.latest_verify_entry` matches on repo, `build_state.verify_record` and `verify_lookup` take an optional member and resolve its commit in the member checkout, and the build driver records a member row when the member landing's parent is the member base. Members join the coordinator project on purpose; member ledger rows retain full Verify output like coordinator rows, while the task Log carries an output tail. Coordinator-only readers (`isolation`'s ledger pass, `lean_verification.verify_project`) keep the coordinator key. | S4a1 Member project Verify | When `.project/build/members.json` locks members, `lean_verification.verify_project` checks out each locked member's bound branch tip beside the coordinator's `project-verify` sidecar, in a folder named after the member checkout, on branch `gsd-path-verify/<coord>-<member>` (`isolation.isolate_member_verify`). Project Verify runs in the coordinator sidecar, so `../<member>` resolves. The member sidecars are removed after the command (`retire_member_verify`); a member setup failure also retires the coordinator sidecar. The result's execution names each member head. Member heads are not in the ledger key, so a member milestone never reads or writes a project Verify ledger row and runs Verify each time; the gap review names the member heads instead of a ledger row. `reuse_final` refuses while members are locked, because wave reviews name only the coordinator head; S4a2 adds member reviewed heads. |

Plan checks reject a task for a member already integrated in this milestone. Change `integration`, `archive_milestone`, `git_guard`, `pipeline_state`, `pipeline_undo`, `pipeline_diagnose`, `status_runtime`, and `pipeline_git` together. Final review binds a reviewed HEAD for each member. The exact ship body keeps the coordinator's `Reviewed-HEAD` and adds `Member-Reviewed-HEAD: <member>@<sha>` and `Member: <name> <integrate-sha> <tag>` for each member; update all three parsers together. Member close creates no STATE, archive, or ship commit for this milestone; it uses the reviewed HEAD and evidence held by the coordinator. `integration.integrate`, `integrate_pull_request`, and `validate_integrated` gain a member path that checks the merge's second parent against that member's `Member-Reviewed-HEAD`, where they check the ship commit today. In `direct` mode, the merge subject is `integrate: <coord> M00N — merge gsd-path/<coord>-M00N into main`. In `pull-request` mode, the GitHub merge of the member bound branch must be a two-parent merge whose second parent is that reviewed HEAD. In both modes, authorize `refs/heads/gsd-path/<coord>-M00N` at the reviewed HEAD before publishing the bound branch. In direct mode, also authorize `refs/heads/main` at the integration merge SHA, whose second parent is the reviewed HEAD. In either mode, authorize `refs/tags/milestone/<coord>-<archive-name>` at its annotated tag object SHA before pushing the tag. A member tag is `milestone/<coord>-<archive-name>`, an annotated tag on the member merge, built by the same member path in place of `milestone/<archive-name>`. `validate-integrated` checks, for each member: the merge is in the first-parent history of its `origin/main`, its second parent is the recorded reviewed HEAD, and its tag points at that merge. The ship journal records each member as `pending` or `integrated`. Resume verifies integrated members and checks a pending entry against the exact remote merge and tag before retrying. In direct mode, the member path publishes the bound branch before it pushes the merge to `main`, then pushes the tag; today `integration.integrate` pushes `main` first. On resume, if the merge matches, publish only the missing authorized refs (bound branch, tag); if all three match, mark it integrated; a mismatch blocks. Never integrate a member twice. Each member uses its own `direct` or `pull-request` mode; member k+1's PR opens only after member k merges. `validate-integrated` checks all repos. Undo of member landing journals a reset to that landing's proven parent in the member, then reconciles only that task's coordinator record; it refuses once that member commit is an ancestor of its `origin/main`. `bind_next_milestone_branch` and `retire_previous_branch` journal and validate member branch retirement after integration. Retirement deletes the remote member bound branch only with a delete authorization for that ref, tied to its expected remote SHA (the reviewed HEAD); member pre-push accepts a delete only when the remote SHA it reports matches. |

## Brownfield and greenfield

| Case | Handling |
| --- | --- |
| All repos new | S5 creates the coordinator, then adds each member with its own resumable bootstrap journal. |
| Existing Path project adds repos | S1 `members add` creates `.project/MEMBERS.md` at a milestone boundary. Past milestones stay single-repo. |
| Member has its own `.project/` | Allowed only without an active milestone. Joining leaves it untouched; its router refuses a new milestone while bound. Namespaced branches and tags avoid collisions. |
| Member is a GSD Core project | Joins like any repo. Its `.planning/` stays untouched. `gsd-path-migrate` is not part of joining. |
| Member has branch protection | Choose `pull-request` for that member. |

## Proof

Use temp repos with bare remotes. Prove each changed contract through its
executable interface; do not infer multi-repo behavior from host receipts.

- No `MEMBERS.md`: existing single-repo commands and output stay unchanged.
- Brownfield `members add` creates `MEMBERS.md`; ship input validation accepts it, `REPOSITORY.md` stays fixed, and non-`main` defaults are refused.
- A two-repo quick-lane run covers task dispatch, cross-repo milestone Verify from the coordinator sidecar with `../<member>`, final review, ordered ship, and next-milestone branch retirement.
- Namespaced member bound, task, verify, and integrate branches work without colliding with retained member branches or being accepted as coordinator branches.
- S2d denies guarded file-edit requests into a member during plan, including edits from a coordinator session. See S3c3b2 for member sidecar host hooks.
- For a listed member, `members validate` rejects a missing or invalid Git-common-dir marker and names the repair command; `member_role` returns `None` when no marker exists. Member pre-push refuses an unauthorized ref or SHA, accepts the pull-request bound branch at the reviewed HEAD, and accepts direct-mode pushes of the authorized merge to `main`, bound branch at the reviewed HEAD, and annotated tag object to the member tag ref. Each ref accepts only its authorized object. A bound-branch delete is accepted only with a delete authorization whose expected remote SHA matches, and refused otherwise.
- A member with shipped M004 and a missing local tag joins and lands a task without applying its own STATE; an active member milestone is refused.
- A crash between member product commit and coordinator record resumes. Deleting the member commit after the record makes the task not landed. Two parallel tasks sharing Base land in order, with the second landing proved against its actual parent.
- A member Verify ledger row resolves by (command, repo, SHA); older single-repo rows still resolve.
- Before the per-member drift check, a lookahead plan with a member task reopens Plan as unverifiable. The follow-up proves drift against that member's recorded base and tip.
- Ship fails on the second member: the journal records the first as integrated, resume verifies and skips it, then completes the milestone. A crash after a member merge or tag but before the journal update reconciles that pending entry without another integration. A direct close stopped after the bound-branch push resumes with the merge and tag; one stopped after the merge push publishes the missing tag. Branch retirement then succeeds. A new task for an integrated member is refused.
- Ship-body validation binds each member's reviewed HEAD to final review and rejects missing or changed member lines.
- A member closes in `direct` and in `pull-request` mode with no STATE, archive, or ship commit in the member. `validate-integrated` rejects a member merge whose second parent is not the recorded reviewed HEAD.
- A member tag `milestone/<coord>-<archive-name>` does not collide with the member's own `milestone/<archive-name>` tag for the same milestone number.
- Undoing the second of two landings that shared Base keeps the first landing, reconciles only the second task's coordinator record, resumes after interruption, and refuses an integrated member commit.
- Greenfield bootstrap resumes each member from its approved target; a two-repo host proof passes before activation. Single-repo host receipts alone do not count.

## Decisions

1. Member remote default must be `main`; `members add` refuses others.
2. Each member may set `direct` or `pull-request` in `.project/MEMBERS.md`.
   The milestone mode is the default.
3. The coordinator may be a product repo or a dedicated program repo.

## Out of scope

Submodules, nested repos, one task across two repos, non-GitHub remotes, an
atomic close across repos, and `.project/` outside Git.
